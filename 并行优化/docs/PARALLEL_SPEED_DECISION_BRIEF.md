# 混合并行熵模型速度问题与后续决策汇报

## 一、先说结论

当前方法已经取得了明显的完整编解码加速，但加速的主要来源是消除 Python/CompressAI 逐流开销，不是四个 CPU 线程。

在 Landsat8、`lambda=16384`、5 张预热和 30 张正式计时图像上：

| 版本 | 完整压缩时间 | 完整解压时间 |
|---|---:|---:|
| Python 串行熵编码 | 110.67 ms | 117.53 ms |
| 优化前 Native 4-worker | 65.83 ms | 65.42 ms |
| 新 Native 1-worker | 37.86 ms | **35.63 ms** |
| 新 Native 4-worker | **37.23 ms** | 35.85 ms |

新 Native 4-worker 相对 Python 路径：

- 压缩加速约 `2.97×`；
- 解压加速约 `3.28×`；
- 真实码流 BPP、PSNR、MS-SSIM 完全一致；
- 编码端和解码端的量化 latent 逐元素一致。

但新 Native 4-worker 相对 1-worker：

- 压缩只快约 `1.7%`；
- 解压没有稳定收益，差异属于测试波动。

因此，“完整 codec 的四线程加速不明显”是真实现象。继续增加 Python 或 OpenMP 线程数，不会从根本上解决问题。

## 二、为什么四线程没有体现在完整时间上

### 1. rANS 本身已经不是主要瓶颈

微基准表明，在真实尾部码流规模上，四线程 rANS 内核确实有效：

- 纯 rANS 编码约 `2.85×`；
- 纯 rANS 解码约 `2.01×`。

但每张图的尾部 rANS 只占完整 codec 的不到几毫秒。即使把这部分完全消除，也不可能将 37 ms 的完整时间变成四分之一。

### 2. 四个尾部组“批量计算”不等于计算量变成四分之一

当前四个尾部组已经沿 batch 维度堆叠，Anchor 和 Non-anchor 各只调用一次共享概率网络。这减少了依赖阶段和网络调用次数，但单张 GPU 仍然需要完成四组的全部卷积计算。

### 3. 前缀仍然有 6 个真实串行阶段

当前分组为：

```text
[16, 16, 32 | 64, 64, 64, 64]
```

三个前缀组分别执行 Anchor → Non-anchor，因此有 6 个串行阶段；尾部再增加 2 个共享阶段，总依赖深度为 8。

对解码端而言，后一阶段必须等待前一阶段解出符号，然后才能预测下一组概率。这是结构依赖，不是增加 CPU 线程能解决的问题。

### 4. 剩余时间主要在神经网络和 CPU/GPU 同步

目前的主要开销已经变为：

- Mamba Encoder/Decoder；
- HyperEncoder/HyperDecoder；
- 前缀和尾部概率参数预测；
- Anchor/Non-anchor 之间的依赖；
- GPU 概率参数与 CPU 熵编码之间的数据传输和同步。

这也是参数量更小的 Hybrid 仍然可能比某些大模型慢的原因：参数量不能直接代表编解码延迟。

## 三、已经完成的优化

1. 四个尾部组使用两个批量概率预测阶段。
2. 四个尾部组建立独立 Anchor/Non-anchor 真实码流。
3. 原生 C++/OpenMP rANS 后端已释放 GIL。
4. CDF 表已缓存，避免重复转换。
5. 三个前缀组的 6 条码流也已改用原生 rANS，不再经过慢速的 CompressAI Python/list 路径。
6. 修复后完整压缩从 65.83 ms 降至 37.23 ms，完整解压从 65.42 ms 降至 35.85 ms。
7. 已验证真实码流、RD 指标与量化 latent 一致性。

这些结果说明，目前的工程实现是有效的，但已经接近“不改结构”条件下的收益上限。

## 四、与 HPCM 的差距如何看

HPCM 先导结果约为：

- 压缩 24.99 ms；
- 解压 23.48 ms。

当前 Hybrid Native 4-worker 约为：

- 压缩 37.23 ms；
- 解压 35.85 ms。

从先导数据看，Hybrid 仍比 HPCM 慢约 49%–53%。但 HPCM 当前是 5 张图像先导测试，Hybrid 是 30 张图像测试，两者 RD 点也没有严格对齐。因此这只能说明 HPCM 目前仍有速度优势，不能直接写成同等质量下的最终加速对比。

后续必须使用同一批 30 张图像、同一计时边界和尽可能接近的 RD 点重测 HPCM。

## 五、后续可选方案

### 方案 A：保留当前结构，只做编码端工程收尾

把编码端的 6 条前缀流和 8 条尾部流延迟到概率预测完成后，一次性提交 14 条流给原生后端。

优点：

- 不需要重新训练；
- 不影响 RD 性能；
- 可以减少多次 GPU→CPU 同步和跨语言调用。

限制：

- 主要优化压缩端；
- 解码端的真实依赖无法用这种方式消除；
- 预期是数毫秒级改善，不是倍数加速。

### 方案 B：新建 Hybrid-V2，将三个前缀组降为两个（推荐）

```text
当前：[16, 16, 32 | 64, 64, 64, 64]  依赖深度 8
V2：  [16, 48     | 64, 64, 64, 64]  依赖深度 6
```

优点：

- 保留一个小的 16 通道 seed group；
- 仍然保留“不均匀串行前缀+均匀并行尾部”的主要创新逻辑；
- 前缀概率预测和解码依赖从 6 阶段减少到 4 阶段；
- 比直接改成单个 64 通道前缀更容易保持 RD 性能。

代价：

- 需要重新训练；
- 需要重新进行 RD 与完整 codec 测试；
- 存在一定 RD 下降风险。

### 方案 C：单前缀的激进版本

```text
V3：[64 | 64, 64, 64, 64]  依赖深度 4
```

优点是理论依赖最低，解码端最有可能继续降低延迟。问题是丢失了前缀逐步建模能力，RD 风险明显高于 V2。该版本适合作为速度上限消融，不建议直接替代主方法。

## 六、建议的决策

建议不再投入时间继续调整 Python 线程数或 OpenMP 线程数，而是采用以下顺序：

1. 保留当前 Hybrid 作为已完成基线，默认部署使用 Native 1-worker，因为它与 4-worker 速度等价且 CPU 占用更低。
2. 先完成方案 A 的 14 流统一提交，确定不改结构时的实际速度上限。
3. 新建 Hybrid-V2，使用 `[16,48 | 64×4]` 进行重新训练和消融。
4. 只将 V3 作为速度上限对照，不作为第一优先级。
5. 用同一批 30 张图像重测当前 Hybrid、V2、原始 Mamba 和 HPCM。

推荐决策为：

> 批准“当前版本工程收尾 + Hybrid-V2 结构实验”两条线并行推进。不再将四线程倍数加速作为目标，而是以降低完整编解码延迟、控制 RD 损失为最终判断标准。

## 七、论文中可以和不可以使用的表述

可以使用：

- 提出了不均匀串行前缀与均匀并行尾部相结合的混合熵模型；
- 概率模型、独立码流和原生 rANS 后端保持一致的并行依赖图；
- 原生完整路径相对 Python 串行路径实测压缩/解压加速约 `2.97×/3.28×`；
- 真实码流、RD 指标和量化 latent 一致。

不可以使用：

- 不能宣称四线程带来四倍完整 codec 加速；
- 不能把依赖深度减少直接等同于实测加速比；
- 不能在 RD 点和测试图像未对齐时声称严格的同质量加速；
- 当前不能声称编解码速度达到 SOTA。

## 八、需要决策者确认的事项

1. 是否同意将 Native 1-worker 作为当前版本默认实现，4-worker 保留为熵内核并行消融。
2. 是否同意完成编码端 14 流统一提交的工程优化。
3. 是否同意新建 Hybrid-V2，对 `[16,48 | 64×4]` 重新训练。
4. 是否同意将“完整 codec 延迟 + RD 性能”作为主要验收标准，不再以线程数或理论依赖深度代替实测结果。
